# とち介商品券2026 マップ サーバー要件

**このアプリを置くサーバーに何が要るか**をまとめたもの。別のサーバーへ移すとき、
ホスティングを検討するとき、サーバー管理者に条件を伝えるときに使う。

利用者側（PC・スマートフォン）の条件は `doc/動作環境.md`、
日々の更新手順は `doc/運用手順.md`、設計の理由は `CLAUDE.md` にある。

現在の公開先: https://www.ngmix.com/tochisuke/ （さくらのレンタルサーバ・共用）

---

## 1. 結論

**静的ファイルを返せるサーバーがあればよい。** サーバー側で動くプログラムは一つも無い。

配信するのは **22 ファイル・合計 1.1 MB**。これを置くだけで動く。

```
index.html            トップページ（これ 1 枚だけ）
404.html
404/index.html
index.txt
shops.json            加盟店データ 683 件（155 KB / gzip 31 KB）
_next/static/css/     CSS 1 本
_next/static/chunks/  JS 15 本（ファイル名に内容ハッシュが入る）
_next/static/<buildId>/
```

Apache でも nginx でも、S3 + CloudFront、Netlify、Cloudflare Pages、GitHub Pages でも動く。

---

## 2. 必須要件

| # | 要件 | 理由 |
| --- | --- | --- |
| 1 | **静的ファイルの配信**。ディレクトリへの要求に `index.html` を返せること | `trailingSlash: true` で `404/index.html` の形に出力される。ほぼ全ての Web サーバーが既定で対応している |
| 2 | **`/tochisuke/` 配下に置くこと** | 公開パスが**ビルドに焼き込まれている**（後述）。別のパスに置くなら再ビルドが要る |
| 3 | **HTTPS** | 「近い順」（Geolocation API）はセキュアコンテキストでしか動かない。`http://` でも一覧・検索・地図は動くが、現在地だけ使えない |
| 4 | `.json` `.js` `.css` の MIME 型を正しく返すこと | 通常は既定で問題ない |
| 5 | Google Maps API キーの**リファラー制限にそのドメインが登録されていること**（サーバーではなく Cloud Console 側の設定） | 未登録だと地図だけが `RefererNotAllowedMapError` で出ない |

### 要件 2 は壊れ方が分かりにくい

ビルド成果物には公開パス `/tochisuke` が埋め込まれている。HTML は `/tochisuke/_next/…` を、
JS は `"/tochisuke" + "/shops.json"` を要求する。**ルート直下に置くと次のようになる**（実測）。

```
GET /                     → 200   index.html は返る
GET /tochisuke/_next/…    → 404   HTML が要求する先が無い
```

HTML だけ返って JS が 404 になるため、**画面はヘッダーだけ出て「読み込み中…」で止まる**。
真っ白にならないので原因に気付きにくい。

---

## 3. 不要なもの

**以下は一切要らない。** ホスティングを選ぶときの条件から外してよい。

- **Node.js ランタイム・常駐プロセス** — SSR / API Routes / Server Actions を使っていない
- **データベース** — 加盟店データは `shops.json` を静的配信するだけ
- **PHP・cron・ジョブ実行環境**
- **rewrite / SPA フォールバックの設定** — ページは 1 枚だけで、クライアント側ルーティングをしない
- **CORS 設定** — `shops.json` は同一オリジン。外部へ出るのは Google Maps だけ

いまのさくらのレンタルサーバは「常駐プロセスが禁止で静的ファイルしか置けない」という
制約から選ばれているが、**この制約は移行先を狭めない**。上の要件を満たすなら何でもよい。

---

## 4. 別のサーバー・別のパスに移す手順

```bash
# 1. 公開パスが変わるなら再ビルドする（ルート直下に置くなら空文字）
NEXT_PUBLIC_BASE_PATH=/new-path bun run build

# 2. out/ の「中身」を転送する（out/ ディレクトリごとではない）
```

3. **Google Cloud Console で Maps API キーのリファラー制限を新しいドメインに変える。**
   `https://example.com/*` の形にし、**パスを含めないこと**。ブラウザは既定のリファラー
   ポリシーでクロスオリジン要求からパスを落とすため、パス付きの制限は正しい要求まで弾く。

4. `bun run preview` で新しいパスの配置を再現して確認してから転送する。

### ビルドに焼き込まれるもの

| 値 | 変数 | 変えたら |
| --- | --- | --- |
| 公開パス `/tochisuke` | `NEXT_PUBLIC_BASE_PATH` | **再ビルドが必要** |
| Maps API キー | `NEXT_PUBLIC_GOOGLE_MAPS_API_KEY` | **再ビルドが必要** |
| Map ID | `NEXT_PUBLIC_GOOGLE_MAPS_MAP_ID` | **再ビルドが必要** |

`NEXT_PUBLIC_` が付く変数は**成果物に必ず入る**。API キーがブラウザから見えるのは避けられない
仕様であり、**秘匿ではなく Cloud Console 側の制限（リファラー・API・割り当て上限）で守る**。

---

## 5. あると良いもの（無くても動く）

| | 効果 |
| --- | --- |
| gzip / brotli | `shops.json` が 155 KB → 31 KB になる。体感に効くのはここ |
| キャッシュ制御 | `_next/static/` は内容ハッシュ付きなので長期キャッシュしてよい。**`index.html` と `shops.json` は短く**（長いとデータ更新が反映されない） |
| `404.html` を 404 に割り当て | 無ければ標準の 404 が出るだけ |
| HTTP/2 | ファイルが 22 個あるので多少効く |

---

## 6. 落とし穴

- **CSP を既定で入れるホスティング**（一部の PaaS）では調整が要る。
  古い端末に理由を出す見張りが**インラインスクリプト**で、地図は
  `maps.googleapis.com` から読み込む。`script-src` にこの 2 つの許可が必要。
  いまのサーバーは CSP 無しで動いている。
- **`data/` を公開領域に置かないこと。** 市から届いた原本 Excel が入っている。
  配信するのは `out/` の中身だけで、`out/` に xlsx は 1 件も入らない（確認済み）。
- **転送漏れ。** ビルドし直したら `_next/` 配下も一式上げる。HTML だけ新しくすると
  参照先のチャンクが無く、「読み込み中…」で止まる。
- **古いファイルが残る。** 差分アップロードを続けると `_next/static/` に使われない
  チャンクが溜まる。内容ハッシュ付きなので実害は無いが、気になれば公開先を空にしてから全転送する。

---

## 7. ビルドする側（サーバーではなく手元）

- **Bun**（`bun install` → `bun run build` で `out/` が出る）
- **サーバー上ではビルドしない。** 成果物を転送するだけ。
- **データだけの更新なら再ビルドも不要。** `shops.json` は実行時に `fetch` する設計なので、
  加盟店リストの更新は `public/shops.json` 1 ファイルの差し替えで済む（`doc/運用手順.md` 6 章）。
